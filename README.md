# Subtitle Translator

字幕翻译工具：读取 SRT / WebVTT 字幕，批量翻译后导出。

PySide6 桌面界面 + 可插拔翻译后端。整条链路（读取 → 翻译 → 导出）已打通并有测试覆盖。
已内置一个 **OpenAI 兼容**翻译后端，可对接任何暴露
`POST {base_url}/chat/completions` 的服务（OpenAI、各类中转/聚合网关、本地推理服务）。

## 配置

API 地址、密钥、模型**都能在界面里改**，不必手写 JSON。两种方式落到同一个
`config.local.json`，改哪个都行。

### 方式一：界面里配置（推荐）

主窗口点「设置…」：

| 项 | 说明 |
| --- | --- |
| API 地址 | 填到 `/v1` 为止，代码自行拼 `/chat/completions` 与 `/models` |
| 密钥文件 | 填密钥文件的路径（推荐，配置里不留副本），带「浏览…」 |
| 明文密钥 | 直接写密钥；留空则回退到密钥文件 |
| 生效密钥 | 实时显示运行时**实际会用哪个**。环境变量优先级最高，被它覆盖时会明确提示 |
| 模型 | 点「拉取模型」从服务端 `/models` 取回列表下拉选择；**也可以直接手输**列表里没有的 id |
| 其余 | 批量大小 / 超时 / 温度 / 保留换行 / 风格提示 |

几个实现上的取舍：

- **拉取模型在网络线程里跑**，后台 QThread + 信号回主线程。点一下按钮窗口不该假死。
- **拉取超时封顶 60 秒**，不复用翻译的 `timeout`（那个默认 120 秒，等列表等不起）。
- 保存时先把原文件备份成 `config.local.json.bak`，再写临时文件原子替换，避免写坏配置。
- 主窗口上的模型下拉是**临时**切换，当次运行生效；要持久化就进「设置…」保存。

### 方式二：直接编辑配置文件

复制模板后填写：

```
copy config.example.json config.local.json
```

```jsonc
{
  "translation": {
    "engine": "openai",
    "base_url": "https://your-endpoint.example.com/v1",
    "model": "your-model-id",
    // 二选一：api_key_file 指向密钥文件（推荐，配置里不留密钥副本）
    "api_key_file": "",
    "api_key": "",
    "batch_size": 20,
    "timeout": 120,
    "temperature": 0,
    "preserve_line_breaks": true,
    "stream": true,
    "style_hint": ""
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `engine` | 注册表里的引擎名；`openai` 为 OpenAI 兼容后端，`echo` 为离线占位 |
| `base_url` | 到 `/v1` 为止，代码会自行拼 `/chat/completions` 与 `/models` |
| `model` | 模型 id，必须存在于服务端 `/v1/models` 返回的列表中 |
| `api_key_file` | 密钥文件路径，运行时读取；**推荐**，避免密钥出现副本 |
| `api_key` | 直接写明文密钥（优先级低于环境变量、高于 `api_key_file`） |
| `batch_size` | 单次请求携带多少条字幕 |
| `preserve_line_breaks` | 保留字幕行内换行结构，多行条目不被合并成一行（默认 `true`） |
| `stream` | 用流式（SSE）接收响应，让「取消」立刻生效（默认 `true`；中继的流式实现有问题时设 `false` 退回整段接收） |
| `style_hint` | 追加到 system prompt 的风格/术语约束，如 `"人名保留原文"` |

环境变量优先级最高：`SUBTITLE_TRANSLATOR_API_KEY` / `SUBTITLE_TRANSLATOR_BASE_URL` /
`SUBTITLE_TRANSLATOR_MODEL`。`config.local.json` 已被 `.gitignore` 屏蔽。

### 密钥安全

密钥只在运行时从 `api_key_file` 读取，**不复制、不落库、不进日志**：

- `TranslationConfig.resolve_api_key()` 每次现读；
- `AppConfig.describe()` 只报告密钥来源（`env:` / `file:` / `config:`），从不输出内容；
- 后端的 `__repr__` 输出 `api_key=<hidden>`，避免异常回溯带出密钥。

## 界面响应性（翻译为什么不冻结窗口）

一部上千条的字幕要分批发几十次请求、每批 3–5 秒，整个翻译是**分钟级**的操作。
早期实现直接在界面线程里调 `translate_cues()`，那段时间主线程被网络等待完全占住：
进度条不重绘、按钮点不动、连「取消」都点不了 —— 用户只能看着程序像死了一样。

现在翻译跑在 `app/ui/translate_worker.py` 的 `TranslateWorker`（QThread）里，
进度与结果通过信号回到主线程（信号跨线程是排队投递的，槽仍在主线程执行，
可以安全碰界面对象）。配套的三件事：

- **翻译期间锁住会改变任务输入或结果的控件**（添加文件 / 设置 / 引擎 / 语言 /
  模型 / 上下文窗口 / 导出 / **队列列表**）。不锁的话，用户中途换字幕文件，后台线程
  还在往旧对象里写译文，界面最终会显示一份与当前文件对不上的结果 —— 而且看不出
  哪里错了。列表也要锁：点一下就能把**另一份**字幕摆进编辑器，同样会错位。
- **提供取消，而且点了就停。** 请求默认走流式接收（`stream: true`），响应一个分片
  一个分片地到，取消在分片之间生效 —— 延迟上限是**一个轮询间隔（0.2 s）**，
  不是一批的时间。已经完整收到的那几条也会保留。详见下一节。
- **关窗先送走线程**（`closeEvent`）。窗口对象一被回收，还在运行的 QThread
  会踩到野指针，Qt 会报 `Destroyed while thread is still running` 并可能崩进程。

度量方式：用 20 ms 周期的 QTimer 给主线程事件循环打点，看最长一次间隔有多大。
间隔涨到「一批的耗时」（秒级）就说明主线程被占住了，几十毫秒才是正常。

```
.venv\Scripts\python.exe scripts\verify_ui_responsive.py          # 后台线程（当前实现）
.venv\Scripts\python.exe scripts\verify_ui_responsive.py --sync   # 复现修复前的做法做对照
```

实测（`grok-chat-fast`，日文 → 中文）：

| 模式 | 条数 / 批数 | 总耗时 | 主线程最长一次无响应 | 翻译期间事件处理次数 |
| --- | --- | --- | --- | --- |
| `--sync`（修复前） | 40 / 2 | 12.7 s | **12 739 ms** | **0** |
| 当前（后台线程） | 100 / 5 | 39.9 s | **23 ms** | 1 996 |

`--sync` 那一栏的「事件处理 0 次」是关键：整个 12.7 秒里主线程一次事件循环都没跑过 ——
窗口不重绘、按钮不加响应、进度条不动、取消点不了。同样一档速度下，上千条字幕
（约 50 批）会连续冻住五分钟以上。改成后台线程后，主线程最长只停了 23 ms，
和 QTimer 的 20 ms 周期同量级 —— 也就是它只做了信号投递这点活。

## 流式接收（取消为什么能立刻生效）

一次请求可能带 200 条字幕（上下文窗口上限），整批返回要十几秒甚至更久。
如果等整批回来才看得到取消，用户点下按钮之后就是十几秒的「什么都没发生」——
和卡死没有区别。所以请求默认带 `stream: true`，改成边收边解析：

- 响应是一个个 SSE 分片（`data: {...}`），`app/core/engines/openai_compat.py`
  里 `iter_sse_deltas()` 负责读，`ArrayStreamParser` 负责**增量切元素** ——
  不等整段收完，每收完一个完整的字符串元素就交出一条。
- 取消命中时，**已经完整收到的条目照样落盘**（`TranslationCancelled` 会带上
  `items`），不必白等前面那十几秒。
- 抢救回来的条目要过一遍**回抄判据**：取消发生在回抄检查之前，直接落盘会把
  「原样退回的原文」当成译文。宁可少救，不能救回没翻的。

### 三处地方必须离开调用方线程

读阻塞的时候，取消检查根本轮不到。这条路上踩了三个坑，全部实测过：

| 坑 | 症状（实测） | 处置 |
| --- | --- | --- |
| 读取在主线程 | 模型「思考」期间点取消，要等到它开口（延迟 2.0 s，整段 12.5 s） | 读取挪进后台线程（`_StreamReader`），调用方只在队列上等 0.2 s |
| 打开连接在主线程 | 网关把响应头**憋到第一个分片就绪**才发，`urlopen` 阻塞 3.55 s —— 这几秒里取消检查没机会跑（线上 0.5 s 点取消、3.5 s 才返回） | 打开动作也挪进线程（`_open_cancellable`） |
| 关闭连接在主线程 | 读线程握着 `BufferedReader` 的内部锁，`close()` 要拿同一把锁，取消卡在收尾上（延迟 1.68 s，期间取消回调一次都没再被调用） | 关闭丢给后台线程（`_release_stream`） |

> 曾经试过「把 socket 读超时调短，让阻塞的读自己醒来」——那条路在**明文 HTTP** 上
> 成立，但在真实中继（TLS）上超时十几次后就提前收到 EOF，整段内容一个字都收不到。
> 证据与复现脚本：`scripts/probe_stream_read.py`、`scripts/probe_live_stream.py`、
> `scripts/diag_https_stream.py`。所以最终没有碰 socket 的任何内部状态。

### 流式只是优化，坏掉不该让翻译不可用

三条降级路径都通向「一次性接收」，记一笔 `stream_fallback_count`，并在状态栏提示：

| 触发 | 动作 |
| --- | --- |
| 中继没理会 `stream`（`Content-Type` 不是 `event-stream`） | 读全文按整段解析 |
| 流读到一半断了（连接重置 / 读超时 / `IncompleteRead`） | 半截内容没法确认完整性，重发一次整段请求 |
| 声明了事件流却一个分片都没给 | 实测真实中继会**偶发**这样回来，同样退回整段接收再问一次 |

真到了「整段也空手而归」，才会报错并说明可以在 `config.local.json` 里把
`"stream"` 设为 `false`。

## 断点续传（翻译中断后接着翻）

一部上千条的字幕要跑几分钟。中途点取消、关掉窗口、中继抽风、机器休眠 ——
任何一种都会让这一轮白跑。所以每翻完一批就把进度写下来，下次接着走：

```
data/checkpoints/<字幕文件名>-<路径摘要>.json
```

把某一份字幕摆进编辑器时（点队列里的那一项）界面会认出它：翻译按钮变成
「继续翻译」，状态栏提示「上次翻到 N 条」。
点下去会问一次 **继续 / 重新开始 / 取消** —— 用户可能刚换了模型想整份重来，
不能把「继续」做成唯一出路。续传时进度条直接落在断点处，不从头爬。

**什么时候能复用**（三条必须同时满足，否则整条记录作废并说明原因）：

| 条件 | 为什么 |
| --- | --- |
| 源文件路径一致 | 这是「同一件事」的定义 |
| 引擎、模型、源 / 目标语言一致 | 混着接会出现前后文风断裂；换模型通常就意味着想整份重来 |
| 逐条原文一字不差 | 只对条数是不够的：文件被改过而条数不变时，按序号硬套会把 A 的译文写到 B 上 |

不匹配时**不删**记录（换回原模型还能接着用），但一定要把原因说出来 ——
静默从头翻，用户基本发现不了。只有整份翻完之后才删。

**什么时候落盘**：由后台线程负责，两秒一次节流（一批 3–5 秒，没必要每批都写，
Windows Defender 还会跟着扫）。取消、失败、关窗三条收尾路径都会**强制写一次**，
所以最多丢最后两秒的那一批。写失败（磁盘满 / 只读）不会毁掉翻译，但会在状态栏
说明「进度未能保存」—— 让用户以为能续传、实际只能重来，比不给断点更糟。

验证脚本（离线、可重复，用自带的 `echo` 引擎）：

```
.venv\Scripts\python.exe scripts\verify_resume.py
.venv\Scripts\python.exe scripts\verify_resume.py --count 200 --batch 20 --stop-after 60
```

实测（40 条、每批 5 条、翻到第 12 条时中断）：

| 走法 | 实际发出条目 | 批数 |
| --- | --- | --- |
| 不续传（从头再来） | 40 | 8 |
| 续传 | 25 | 5 |

省下 15 条（38%），已翻条目零重复、最终零残留。
注意中断发生在**批与批之间**，所以「翻到第 12 条时取消」实际会翻到批边界（15 条）。

## 上下文窗口与「重试未翻译」

### 上下文窗口：随手的那个旋钮

主界面「模型」右边有「上下文窗口」，就是**单次请求塞给模型多少条字幕**
（和「设置」里的批量大小是同一个参数；设置里改的是下次启动的默认值，
主界面上改的是本次，立刻生效，不用保存、不用重启）。

| 调大 | 调小 |
| --- | --- |
| 请求数更少、更省额度、更快 | 一批失败的影响面更小；个别翻不动的条目更容易被单独拎出来重试 |

它同时也是**出问题时第一个该拧的旋钮**：某几条怎么都翻不动时，把它调到 1 条/次，
那几条就会各占一个请求、各自被判定和重发，比夹在几十条里更容易成功。

翻译期间这个控件会被锁住 —— 它决定这一跑怎么切批，中途改会让「已经翻到哪」
说不清，而界面上的数字又给不出任何提示。

### 自动重试用尽之后：手动重试

一道字幕翻完，若还有条目**一字未改且书写族根本不对**（例如日文假名句译成中文
却还是原样），说明模型没干活。这种事不能静默交付，所以：

1. 状态栏会写「仍有 N 条未翻译（可点「重试未翻译」）」；
2. 多出一个「**重试未翻译（N）**」按钮，只把这几条重新发一遍，不动已翻好的部分；
3. 同时弹一次窗，里面直接就有「重试这些条目」——点下去立刻重跑，不用回头找按钮。

**定罪标准与引擎内部同一套**（`translator.locate_untranslated`）：只有原文的书写族
根本不是目标语言的族、而译文仍与原文相同时才算。日文「学校」译成中文仍是「学校」
这类同形词一律放过；源与目标同族（`zh-CN` 对 `zh-TW`、`en-GB` 对 `en-US`、
中文原文配中文目标）也一律不算。

手动重试和引擎内部的自动重试不是一回事：那两步（整批重发、逐条重译）用的是
**同一份**请求参数，撞一百次也可能还是同样的结果。手动重试之前可以换模型、
可以把上下文窗口调到 1 —— 那才是能真正改变结局的一手，弹窗里也是这么写的。

两个实现上的坑（都是「静默出错」那一类，所以特意写下来）：

- **重试本身不写断点，但会刷新已存在的记录。** 断点记录用 `enumerate` 的下标给
  条目定位，而重试拿到的是原列表的一个子集；子集下标会被当成整份字幕的下标，
  把 A 条的译文记到 B 条名下。整份任务此时已经完成，重试丢了大不了再点一次，
  不值得为它冒这个险。
  但**如果断点还在**（比如中断后重试了几条、然后又想接着翻），就必须按整份字幕
  把记录刷一遍 —— 记录里那几条还是旧的**回抄值**，续传会拿它无条件覆盖
  `cue.translation`，用户刚花掉的那次重试会悄无声息地退回原文。
  （记录不存在、或已不属于当前任务时一律不碰：刷新反而会毁掉一份还有用的记录。）
- **重试不清空旧译文。** 那几条的「译文」本来就等于原文，留着正好当兜底：
  重试中途取消的话，字幕里还有原文可看，而不是变成一片空白。

界面层靠测试覆盖（会真的建窗口、真的起后台线程）：`tests/test_ui_smoke.py` 里
`test_context_window_*` 与 `test_*retry*` 那几组。

## 批量队列（一次添加多个文件，依次翻译）

一集一集地「打开 → 翻译 → 导出」，十几集下来光是重复点按钮就够烦，而且中间
一走开就停在原地。所以**添加字幕只有队列这一个入口**：窗口底部队列里的
**添加文件…** 一次可以选多个字幕，**依次翻译** 把它们逐个翻完并各自落盘，
全程不需要人守着。

| 动作 | 结果 |
|---|---|
| 添加文件… | **唯一的入口，可多选**。读不了、格式不支持、已在队列里的当场剔除并说明原因 |
| 点列表里的某一项 | 把那一份摆进编辑器（核对译文、看条数）；编辑器显示的**始终**是列表里选中的那一行 |
| 依次翻译 | 按列表顺序逐个翻。**每个文件翻完立刻自动导出**，无需点「导出…」 |
| 移除 / 清空 | 只动队列，不碰源文件（队列里存的就是路径，重新选一次即可） |
| 上移 / 下移 | 调整顺序（只对选中的一项生效，多选时不动 —— 语义不清不如不猜） |
| 继续队列 | 上一轮失败或没轮到的重来，**已经翻好的不会白跑第二遍** |

三处避免「静默出错」的细节：

- **队列里没有第二个添加文件的按钮。** 以前顶部还有一个「打开字幕…」，功能重复
  而且只认单选 —— 同一个动作两个按钮、行为还不一样，用户得先猜哪个是哪个。
- **编辑器里已经有一份在看时，加文件不会把它换掉。** 换掉等于把那一份**还没导出**
  的译文从内存里抹掉，而翻译成功后会清掉断点，抹掉就真找不回来了。
- **列表的选中行和编辑器永远指向同一个文件。** 高亮留在上一份上，看起来就像
  「翻译翻错了文件」—— 而译文其实是对的。

「翻译」按钮仍然只翻**当前显示的那一份**（不自动保存），用来先看看效果；
要翻完队列并保存，用「依次翻译」。

### 译文放在哪

`output/<原名>.translated.srt`（或 `.vtt`），与手动「导出…」的默认文件名一致。
源文件所在目录保持干净 —— 一次处理几十个文件也不会把原目录搞乱。

两条命名规则值得知道：

- **同一批里出现同名文件**（不同目录的 `01.srt`）时，后来者变成
  `01.translated-2.srt`。否则后翻完的会把先翻完的覆盖掉，而列表上两份都显示
  「完成」，用户拿到手只有一份却看不出少了什么。
- **磁盘上已存在的同名译文直接覆盖**，不加序号。重跑一遍本来就是要更新上一轮
  的结果；加序号只会让输出目录堆起一堆 `-2` `-3`，谁是最新的反而看不出来。

### 失败与中断

队列是给「人不在场」用的，所以两种打断的处理方式刻意不同：

- **某个文件失败**（中继 502 重试耗尽、导出不了）→ 记下原因、**跳过它继续
  下一个**。整条队列跑完再弹一次窗列出哪几个失败、为什么 —— 只在状态栏留一句
  「2 个失败」等于没说，用户回来时得知道接下来该点什么。
- **点「取消」** → **停下整条队列**。当前这一份打回「待翻译」，断点还在，
  下次点「依次翻译」从它接着往下走。

**队列里不弹那个「继续/重新开始/取消」的三选窗**：人不在场，一个模态框就能把
整条队列永久卡死在第一个文件上。有断点就默认接着上次翻 —— 这正是用户点
「继续翻译」时会选的那一个。翻完的文件会清掉自己的断点，没翻完的留着。

还有两处刻意的设计：

- **推进用循环而不是递归**。一整个队列的文件都读不了时，递归会一层层压进调用栈；
  而「每个文件都在失败」恰恰最容易发生在一批本身就有问题的时候。
- **失败的项不当场自动重来**。否则一个注定失败的文件会被反复重发，队列永远跑不完，
  而用户以为自己只是点了一次「依次翻译」。

## 翻译协议说明

批量翻译时把整批字幕作为一个 JSON 数组送出，要求模型返回等长 JSON 数组。
实测有两个坑，代码里都做了处理：

1. **换行会被模型吃掉。** 只让模型「保留换行符」不可靠，多行字幕常被合并成一行。
   现在送出前把换行替换成可见记号 `⏎`（U+23CE），收回后再还原；若模型仍丢记号，
   则对**该条**按行重译（`line_repair_count` 可观测触发次数）。
2. **批量协议可能被破坏。** 模型加了说明或数量不符时，整批退回逐条翻译，宁可慢也不丢内容。
3. **整批被原样退回（最危险的一种）。** 中继有时会把整个数组原样吐回来 ——
   实测 `grok-chat-fast`（唯一免费档）**请求级**概率约 1/3（各次采样 17%–50%，
   累计 34 批中 11 批），中→日与日→中都会中，且是**整批**而非零散几条。
   这种失败用户看不出来：拿到一份根本没翻译的字幕，界面上一切正常。

   > **根因**（2026-09-26 判别实验，复现脚本 `scripts/probe_echo_mechanism.py`）：
   > **不是模型翻译能力时好时坏，而是同一个模型名下的请求被分发到了能力不齐的后端池。**
   > 四条判据：① 请求体**逐字节相同**的 8 次请求，结果在「整批中文」与「整批日文」
   > 之间跳（排除提示词问题与确定性缓存）；② 机械任务（每个元素加 `[1]`，不需要语言
   > 能力）**8/8 全部执行成功**（请求确实被执行，排除掉线/兜底）；③ 回抄内容**不含**
   > 我们拼进去的 `源语言:` 前缀，且伴随同语言改写（`何度も言ったはずだ。` →
   > `繰り返し言ったはずだ。`）——是真模型在写，不是转发层回吐请求体；
   > ④ 每批只发 1 条也同样回抄（3/8），与「一整个数组」的形状无关。
   > 被推翻的假设：中继丢 system 提示词（指令搬进 user 反而更差）、批量形状、提示词措辞。

   处理方式分三层，代价由小到大：

   | 层 | 触发条件 | 动作 | 观测字段 |
   | --- | --- | --- | --- |
   | 1 | 过半条目与原文一字不差（可比条目 ≥ 3） | 换更严格的提示词**整批重发**，最多 `echo_retries` 次（默认 3） | `echo_retry_count` |
   | 2 | 重发后仍有零星条目没翻 | 只把那几条**拎出来逐条重译**，每条最多 `echo_item_retries` 次（默认 2） | `echo_item_count` / `echo_item_attempts` / `echo_repaired_count` |
   | 3 | 整批可比条目无一翻出来 | **报错**，绝不静默交付未翻译的结果 | `untranslated_count` |

   重试次数是按实测失败率定的：单次回抄率 ≈ 1/3，于是「连续 N+1 次全中」的概率是
   `(1/3)^(N+1)` —— `echo_retries=3` 时降到 1.2%，代价只比 2 次多约 2.6% 的请求。
   逐条那一层同理：每条试 2 次，把单条残留率从 1/3 压到 1/9。

   个别条目救不回来时**不中断任务**（同形汉字词本来就可能原样保留），
   但会计入 `untranslated_count` 并在界面上弹提示 —— 回抄是静默故障，
   不报告就没人会发现手里那份字幕根本没翻。

   > 配额开销与最终残留的实测：`python scripts/measure_echo_cost.py`
   >
   > 实测（`grok-chat-fast`，20 条/批，源语言 `auto`）：
   > 10 轮 / 200 条 → **1.10 请求/批（开销 10%）、0 条残留**；
   > 12 轮 / 240 条 → **1.08 请求/批（开销 8%）、0 条残留**。
   > 开销随中继当时的池子健康度变化很大，按单次回抄率 `p` 折算约 `p + p² + p³`：
   > `p=9%`（本轮实测）→ 10%，`p=33%`（历史均值）→ 48%，`p=57%`（最差采样）→ 108%。
   > 换来的是一次都不静默交付未翻译内容。

4. **源语言选 `auto` 不等于放弃检查。** 界面默认就是 `auto`，早期实现在这里
   直接跳过检查 —— 实测「`auto` + 20 条日文字幕」8 批里有 2 批整批 100% 原样退回，
   全被静默交付。现在按文本的**书写族**去认源语言（见 `detect_script()`）：
   只要出现假名就判日语、谚文判韩语、西里尔/阿拉伯/天城文各有归属，
   纯拉丁与汉字分别归 `latin` / `han`，整批按条目投票取众数（`guess_text_family()`）。

   只有当**源与目标同族**时才真的放过 —— `en-GB`→`en-US`、`zh-CN`→`zh-TW`
   这类转换里大量条目本就该原样，回抄比例天然偏高，判定必然误报。
   `auto` + 中文字幕 + 目标中文同样会被正确识别为同族，不会误报。
   条目的定罪判据也在这一层：**只承认书写族根本不对的条目**，
   日文「学校」译成中文仍是「学校」这种同形词一律放过。

5. **502 / 503 / 504 等链路故障自动重试。** 中继链路上的这类错误是**瞬时**的：
   上游节点被踢下线、后端池在扩容重启、网关健康检查把某台摘掉 ——
   同一份请求过一两秒再发往往就成功了。它和回抄是两回事（回抄是请求被处理了
   但没翻译，得换提示词；502 是请求压根没被正常处理，重发同一份就是对的），
   但后果一样：一批字幕直接卡死、整个任务中断。

   处理方式：**指数退避 + 抖动**重发，默认 `http_retries = 3`（最多 4 次尝试），
   第一次失败等 0.3–0.6 s，之后逐次翻倍，单次等待封顶 8 s；
   服务端给了 `Retry-After` 就照办（封顶 30 s，免得被一个离谱的值挂死）。

   | 状态码 | 重试 | 理由 |
   | --- | --- | --- |
   | 502 / 503 / 504 | ✅ | 网关/上游瞬时故障，重发往往就通 |
   | 429 | ✅ | 限流，等一会儿再发 |
   | 408 / 500 | ✅ | 请求超时 / 上游内部错误，通常也是瞬时的 |
   | 400 / 401 / 403 / 404 / 422 | ❌ | **确定性**失败：密钥错、模型名错、参数非法 —— 重发一百次也是同样结果，只会白烧配额 |
   | 证书校验失败 | ❌ | 同样是确定性失败 |
   | 连接被重置 / 超时 | ✅ | 下一秒重发常常就通了 |

   重试用尽后**原样报错**，并在错误信息里注明「已自动重试 N 次」——
   免得用户以为是偶发失败而反复手点。拉取模型列表走的也是同一个中继，
   同样会重试（`fetch_models(retries=2)`）。

   > ⚠️ 与 `echo_retries` 不同，`http_retries` 的次数**不是**从实测失败率推出来的。
   > 502 无法按需复现：`python scripts/verify_http_retry.py --live 10` 对真实中继
   > 采样（本轮累计 16 个请求，6 + 10）**一个链路故障都没撞上**，用的是常规默认值。
   > 确定性行为（哪些码会重试、退避多久、退避后成功、401 一次都不重试）
   > 由 `scripts/verify_http_retry.py` 在本机起真实 HTTP 服务验证，零配额、可重复。
   >
   > 观测字段：`http_retry_count`（重发次数）、`http_retry_reasons`（如 `{"HTTP 502": 2}`）、
   > `http_retry_waited`（累计等待秒数）；翻译完成后会在状态栏提示。
